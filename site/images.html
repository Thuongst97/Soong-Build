Partitions & Image Generation

The last thing the Android build does is turn staging directories into images. In a head unit those images become a handful of partitions inside a much larger storage layout shared with QNX and Linux — so you must know exactly what each one holds, how big it is, and who verifies it.

8.2boot, init_boot & vendor_boot

The boot image format has evolved through header versions. New devices with GKI use v4, which splits the old boot.img into three images owned by different parties.

HeaderIntroducedLayout
v0 – v2Legacy – Android 10Kernel + ramdisk (+ DTB in v2) all in boot.
v3Android 11boot = kernel + generic ramdisk; new vendor_boot = vendor ramdisk + DTB + vendor cmdline.
v4Android 12Multiple vendor ramdisk fragments, bootconfig for androidboot.* parameters, boot signature for GKI.
v4 + init_bootAndroid 13Generic ramdisk moves to init_boot; boot holds only the GKI kernel.

8.3Dynamic partitions & super

Instead of fixed-size GPT partitions for system, vendor and friends, one large super partition holds logical partitions that can be resized by an OTA. Their layout is stored in LP metadata at the start of super; first-stage init maps them with device-mapper.

ℹ️
Note

The size of super is fixed by the storage layout that also holds QNX and Linux (Module 15). Choose it once with growth margin — changing it later means repartitioning devices in the field.

8.4Android Verified Boot

AVB extends the chain of trust from the bootloader to every byte Android executes. The bootloader holds a public key, verifies vbmeta, and vbmeta carries hashes (small partitions) or dm-verity hashtree roots (large partitions) for everything else.

root key in guest loader→vbmeta→boot · init_boot · vendor_boot · dtbo (hash)→vbmeta_system (chained key)→system · system_ext · product (hashtree)
⚠️
Head-unit specific

In a VM, the code that verifies vbmeta is the guest bootloader (or the hypervisor's loader) — not the SoC's bootloader. Decide early who holds the AVB public key and the rollback indexes, and how the hypervisor's own secure-boot chain vouches for that loader (Module 15).

8.5A/B (seamless) updates

With A/B every updatable partition exists twice (_a/_b). update_engine writes the update to the inactive slot while the car is driving; the next boot switches slots and falls back automatically if the new slot fails to boot. Virtual A/B avoids doubling the dynamic partitions by writing copy-on-write snapshots that are merged after a successful boot.

ℹ️
Note

A/B needs a boot control implementation (the Boot HAL) that the guest bootloader honours — usually by reading/writing slot metadata in misc. In a hypervisor system, slot switching must be coordinated with QNX and Linux updates; see Module 15.7.

8.6target-files, dist & OTA packages

target-files is the build's master archive: the contents of every partition plus metadata and tools input. Every release step — signing, image creation, OTA generation — consumes it, so you never need the build tree again.

8.7Release signing

Development builds are signed with the public test keys in build/make/target/product/security. Anyone can sign with those — a production head unit must be re-signed with private keys that never leave your signing server.
