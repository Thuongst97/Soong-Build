The Android Build System at a Glance

“Soong” is shorthand for a small pipeline of tools. Before writing a single Android.bp, learn which tool reads which file, what each produces, and where the results land in out/. Every later debugging session starts from this picture.

⏱ 20 min read🎯 Beginner📂 build/soong · build/blueprint · build/make

1.1From Make to Soong

Until Android 6 the whole platform was one giant GNU Make program. As AOSP grew past tens of thousands of modules, Make became slow to start (minutes just to parse) and impossible to reason about, because any makefile could change any global variable. Android 7 introduced a split: declarative module files handled by Soong, with legacy makefiles translated by Kati, and both executed by Ninja.

EraWhat changedWhat it means for you
≤ Android 6Pure GNU Make, Android.mk everywhereOld vendor trees and tutorials still look like this.
Android 7 (2016)Soong, Blueprint, Kati and Ninja introducedMake no longer runs commands; it only describes them for Ninja.
Android 8 – 13Most platform modules converted to Android.bp; Android.mk banned in more placesNew modules belong in Android.bp. Product configuration stays in Make.
2020 – 2023Experimental migration to Bazel (“bp2build”), then cancelledIgnore Bazel for the platform; Soong is here to stay. (The kernel does use Bazel — see Module 09.)
Android 14 – 16Release configurations (TARGET_RELEASE), aconfig flags, select() in Android.bplunch now takes product‑release‑variant; conditionals move into Soong.
🎭
Analogy

Think of a restaurant kitchen. Android.bp files are recipe cards, Soong is the head chef who reads every card and writes the prep list, Kati translates the old handwritten recipes into the same list, and Ninja is the line cook who works through it as fast as possible — and skips any dish that is already plated.

1.2The toolchain at a glance

soong_ui

The program behind m. Validates the environment, runs product configuration, then starts Soong, Kati and Ninja in order. Lives in build/soong/ui and writes the logs under out/.

Blueprint

The framework under Soong (build/blueprint): the Android.bp parser, the module and mutator engine, and the Ninja writer. Soong is “Blueprint + Android module types”.

Soong (soong_build)

A Go program compiled at the start of the build. Reads every Android.bp, creates variants, resolves dependencies and emits out/soong/build.<product>.ninja.

Kati (ckati)

A fast GNU Make clone. Evaluates product makefiles, BoardConfig.mk and remaining Android.mk files, and emits Ninja instead of running commands.

Ninja

The executor. Loads the combined manifest, compares timestamps and command lines, and runs only the out-of-date actions in parallel.

Prebuilt toolchains

Go (prebuilts/go), Clang (prebuilts/clang/host), JDK (prebuilts/jdk), build tools (prebuilts/build-tools). The build uses these, not the host's compilers.

Tip

If nothing changed in any Android.bp or makefile, the generate stage is skipped — soong_ui checks file globs and timestamps — and the build goes straight to Ninja. That is why a no-op incremental build takes seconds while the first build after a repo sync takes minutes before compiling anything.

1.4Modules, variants and the build graph

A module is one block in an Android.bp — a library, binary, app or file. Soong runs mutators over all modules; some split a module into variants, one per configuration it must be built for. Dependencies are then resolved variant-to-variant: a 64-bit vendor binary links against the 64-bit vendor variant of a library, never the system one.

That one module becomes several variants. Each gets its own directory in out/soong/.intermediates/:

out/soong/.intermediates/vendor/acme/libgreet/libgreet/ ├── android_arm64_armv8-a_shared/ # system, 64-bit, .so ├── android_arm64_armv8-a_static/ # system, 64-bit, .a ├── android_arm_armv8-a_shared/ # system, 32-bit (if the product is multilib) ├── android_vendor_arm64_armv8-a_shared/ # /vendor variant (vendor_available) └── linux_glibc_x86_64_shared/ # host variant (host_supported)

os × arch

android, linux_glibc, linux_bionic, windows × arm64, arm, x86_64, x86, riscv64.

image

core (system), vendor, product, recovery, ramdisk, vendor_ramdisk.

link & apex

shared / static, plus apex<min_sdk> variants for code that ships inside an APEX.

ℹ️
Note

Variants are why you cannot “just add an if” to an Android.bp. Soong must know statically every combination a module can be built in, so variation is expressed through properties such as arch: {}, target: {} and select() (Module 03).

1.5Anatomy of out/

Everything the build creates lives under out/ (or $OUT_DIR). Knowing the layout turns “where did my file go?” into a one-line ls.

out/ ├── error.log verbose.log.gz soong.log build.trace.gz # start here when a build fails ├── combined-<product>.ninja # what Ninja actually executes ├── build-<product>.ninja # Kati output (Android.mk + product) ├── soong/ │ ├── build.<product>.ninja # Soong output │ ├── soong.<product>.variables # product config as JSON │ ├── .intermediates/<path>/<module>/<variant>/ # per-variant objects, jars, gen/ │ └── host/linux-x86/bin/ # host tools built by Soong ├── host/linux-x86/ # host tools: avbtool, lpmake, aapt2, fastboot… ├── target/product/<device>/ # $ANDROID_PRODUCT_OUT │ ├── system/ vendor/ product/ system_ext/ odm/ # staging dirs = partition contents │ ├── boot.img init_boot.img vendor_boot.img super.img vbmeta.img │ ├── module-info.json # every module, its path and install files │ └── obj/ # Make-built intermediates └── dist/ # only with `m dist`: target-files, img zip, symbols
⚠️
Warning

out/ for a full AAOS product easily reaches 250–400 GB. Put it on a fast local NVMe disk, never on NFS. Use OUT_DIR=/fast/disk/out if the source tree is elsewhere.

1.6Key takeaways

Generators vs executor

Soong and Kati only write Ninja files. Ninja runs every compiler, linker and image tool.

Android.bp is declarative

No loops, no if. Variation comes from variants and configurable properties.

Product config is still Make

PRODUCT_* and BOARD_* variables are evaluated by Kati and passed to Soong as JSON.

out/ tells the story

Logs at the top, Soong state in out/soong, partition staging in out/target/product/<device>.
