QNX Hypervisor Host

The host is the first OS to run and the last to fail. It is a QNX Neutrino system whose job is small but critical: own the hardware, start one qvm per guest, serve their virtual devices and watch their health. Its image is built with the QNX toolchain — no Soong involved.

11.1Hypervisor concepts

Microkernel + virtualization

The QNX Neutrino microkernel (procnto) runs at the hypervisor exception level. Everything else — drivers, file systems, and each VM — is a normal, restartable process.

One qvm per guest

A qvm process creates one VM from a configuration file: guest RAM, vCPUs (host threads), and the virtual devices it loads as shared objects.

vdevs

Virtual devices emulated inside qvm: interrupt controller, UART, virtio block/net/console, shared memory, watchdog. They forward I/O to host drivers.

Pass-through

A physical device mapped directly into one guest (USB, Wi-Fi). Fast, but that guest now owns it; the SMMU confines its DMA.

🎭
Analogy

Each qvm is a flight simulator cockpit: the guest pilot believes it flies a real plane, but every instrument (vdev) is driven by the simulator, and only the few real controls you deliberately wired in (pass-through) touch actual hardware.

11.2Installing QNX SDP

Install with the QNX Software Center using your license: the SDP (7.1 or 8.0, as your BSP requires), the Hypervisor add-on and the SoC BSP. Record the exact package versions — they are part of your release (Module 10.6).

💡
Tip

For CI, install the SDP once into a read-only directory or container image and export the package list from the Software Center. A different patch level of libc or a driver is a different product.

11.4Host buildfile & mkifs

A QNX bootable image is an IFS (image file system) created by mkifs from a buildfile. The buildfile has three parts: the boot loader stub (startup + kernel), a startup script, and the list of files to include.

11.5qvm guest configuration

Each guest is described by a text file passed to qvm. It is the VM's “hardware”: whatever is not listed here, the guest simply does not have.

ℹ️
Note

Guest-physical addresses (loc) and interrupt numbers are virtual: they only need to be unique inside one VM and consistent with what the guest kernel expects. qvm can generate the guest's device tree from this file, which is why the Android guest needs no hand-written DTB.

11.7Pass-through devices

Pass-through maps a device's MMIO registers into the guest and routes its interrupt. Because the device can DMA, the host must program the SMMU (on QNX, through the SMMU manager service) so the device can only reach that guest's RAM.

  • Remove the device from the host's own startup script — two drivers for one device is a classic bring-up bug.
  • Describe the device to the guest exactly as its driver expects (compatible string, clocks may need a para-virtual workaround).
  • Power and clocks often stay host-owned: the guest driver cannot turn them on by itself.
