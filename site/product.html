Product & Board Configuration

Android.bp says how to build a module; the product configuration says what goes into this device's images and how the hardware looks. It is still written in Make, evaluated by Kati and handed to Soong as JSON.

⏱ 30 min read🎯 Intermediate📂 device/<company>/<device>

5.1Device tree layout

All product configuration for one board lives in a device tree (unrelated to the kernel's DTB). This handbook's example company is Acme and the board is hu:

device/acme/hu/ ├── AndroidProducts.mk # which products exist (→ lunch choices) ├── acme_hu.mk # the product: name, brand, inherited products ├── device.mk # packages, copy files, properties for this device ├── BoardConfig.mk # arch, partitions, kernel, AVB, sepolicy dirs ├── Android.bp # soong_namespace + device-local modules ├── init/ # init.hu.rc, fstab.hu, ueventd.hu.rc ├── sepolicy/vendor/ # device SELinux policy ├── overlays/ # RROs: CarService, SystemUI, framework config ├── audio/ display/ vhal/ # config files for HALs ├── manifest.xml # VINTF: HALs served by /vendor └── compatibility_matrix.xml # VINTF: what vendor needs from system device/acme/hu-kernel/ # prebuilt GKI + vendor modules + DTB (Module 09) vendor/acme/ # HAL sources, prebuilt blobs, shared vendor code

5.2AndroidProducts.mk & lunch choices

The build scans device/*/*/AndroidProducts.mk and vendor/*/*/AndroidProducts.mk. Each lists the product makefiles it provides.

5.3The product makefile

VariablePurpose
PRODUCT_PACKAGESModule names to install (Module 04.9).
PRODUCT_COPY_FILESsrc:dest pairs copied verbatim. Prefer prebuilt_etc modules for anything non-trivial.
PRODUCT_VENDOR_PROPERTIES · PRODUCT_PRODUCT_PROPERTIESSystem properties in /vendor/build.prop · /product/etc/build.prop.
PRODUCT_SOONG_NAMESPACESWhich soong_namespaces are visible to this product (Module 06).
PRODUCT_SHIPPING_API_LEVELThe API level the device first shipped with — drives VTS and compatibility requirements.

5.4Product inheritance

inherit-product evaluates another product makefile and merges its PRODUCT_* variables into yours: list variables are combined, single values set in your file win. This is how one line pulls in the hundreds of packages that make Android “automotive”.

acme_hu.mk⇢car.mk⇢car_generic_system / car_product …⇢core_64_bit_only.mk⇢base product makefiles

inherit-product

Proper product inheritance with merging and de-duplication. Use for *.mk files that define PRODUCT_* variables.

include

Plain textual inclusion. Use for BoardConfig fragments, never for product files (values silently overwrite each other).

5.6Release configurations

The middle part of the lunch target (TARGET_RELEASE) selects a release configuration: a set of values for RELEASE_* build flags and runtime aconfig feature flags. Release configs are declared as textproto files under build/release/; vendor directories can add their own with a release_config_map.textproto.

5.7Passing config to Soong

Soong cannot read arbitrary Make variables. Values flow one way through Soong config variables, grouped in a namespace:

device.mk: soong_config_set→soong.<product>.variables (VendorVars)→select() / soong_config_module_type

5.8Automotive product specifics

Inherit the car product

car.mk (in packages/services/Car/car_product/build/) adds CarService, the car framework, Car UI apps and sets PRODUCT_CHARACTERISTICS := automotive. Split variants exist for products that need a GSI-compatible system image.

Declare the feature

Copy android.hardware.type.automotive.xml to /vendor/etc/permissions; without it the device is not recognised as a car.

Replace the reference VHAL

The emulator products install the default VHAL. A real head unit ships its own VHAL service that talks to the vehicle network (Module 13).

Configure through overlays

Occupant zones, audio zones, UX restrictions and displays are configured in CarService's config.xml via an RRO plus XML files in /vendor/etc.
