Full Image Integration, Boot & Flashing

Four builds produced a dozen images. This module turns them into one product: a storage layout that holds them all, a boot chain that verifies each one, a single script that builds and packs everything, and an update scheme that keeps four operating systems in step.

15.1Storage layout

UFS devices expose several logical units (LUNs), each with its own GPT. Giving every OS its own LUN keeps ownership obvious: the host exports LUN 2 to Android and LUN 3 to Linux as whole virtio disks, and no guest can see another's partitions. Click a partition.

15.2Firmware & secure boot chain

Each stage verifies the next before running it. The chain starts with a key hash fused into the SoC and ends with AVB inside the Android guest.

⚠️
Irreversible

Fusing the secure-boot key hash cannot be undone. Lab boards stay unfused; production keys live in an HSM and are only used by the release signing pipeline. A board fused with the wrong key is scrap.

15.4One script to build everything

Developers and CI must build the product the same way. One script, driven by release.yaml (Module 10.6), runs the four builds, collects their outputs into a staging directory and hands over to packing.

15.5Packaging the flashable bundle

The pack step reads storage.yaml, checks every image fits its partition, generates one GPT per LUN, signs the images it owns, and writes a manifest with hashes so the flasher (and the factory) can verify the bundle.

💡
Tip

Make the pack tool fail hard when super.img is bigger than the super partition or when BOARD_SUPER_PARTITION_SIZE differs from storage.yaml. Catching it here saves a bricked board on the bench.

15.6Flashing the board

Factory and first-time flashing use the SoC vendor's USB download mode and tool (they can write any LUN, including firmware, on an empty device). Day-to-day development is faster with fastboot, if your bootloader provides it:

ℹ️
Faster iteration

While working only on Android, rebuild one image (m vendorimage → m superimage) and flash only that partition. With a running Android you can also push to a userdebug build with adb remount + adb sync vendor.

15.7Updating four OSes

Every component has A/B slots, but the product must switch as a whole: a QNX host from release N with an Android from release N+1 is a combination nobody tested. The Linux SE OTA orchestrator therefore treats a release as one unit.

download signed bundle→verify manifest→write inactive slots: fw · hyp · cluster · linux→Android: update_engine payload→switch all slots→reboot · health check · commit or roll back
  • Android's payload comes from ota_from_target_files on the signed target-files (Module 08.6).
  • The host health monitor counts boot attempts per VM; if a VM fails to come up on the new slot, the whole system falls back.
  • Only after all VMs report healthy does the orchestrator mark the new slot successful (Android: update_verifier + Virtual A/B merge).

15.8CI pipeline

Cache everything

ccache and a reused out/ for Android, sstate and downloads for Yocto. A cold full build takes hours; a warm incremental one, minutes.

Test on hardware

A hardware-in-the-loop rack flashes every candidate and measures cluster and Android boot times — regressions in the boot budget are bugs.
